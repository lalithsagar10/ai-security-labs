The idea in one minute

What RAG is, and why it is harder to secure than a chatbot

In Part 1 the chatbot only saw two things: its system prompt and your message. A RAG app adds a third: documents it looks up and pastes into the prompt before answering. The model reads those documents with the same attention it gives your instructions.

That creates the defining RAG problem. An attacker no longer has to talk to the bot. They can hide instructions inside a document, wait for it to be retrieved, and let the app deliver the attack for them. And because everyone's documents sit in one vector database, a missing filter means one user can read another's data just by asking the right question.

1 · User → app. The server decides the role from the login, never from anything the user types.

4 · Model → user. Check the answer for canaries, restricted text and unsafe links before returning it.

Tools

What each tool is and what it does for us

Three groups: tools that build the app, tools that attack it (all reused from Part 1), and standards we use to label findings.

Build the app

Ollama

build

Runs open-weight models on your Mac, so the target is free and nothing leaves the machine.

In Part 2: two models. llama3.2 writes answers (already installed). nomic-embed-text turns text into vectors (new, ~270 MB).

Embeddings

build

An embedding is a list of numbers that captures what a chunk of text means. Texts with similar meaning get similar numbers, which is how "refund rules" finds a doc titled "Returns policy".

In Part 2: the attack surface for LLM08. Crafted text can be made to sit "near" queries it has nothing to do with.

Chroma

build

A lightweight vector database. It stores each chunk with its vector and a metadata dictionary, and returns the closest chunks to a query.

In Part 2: the metadata (access, source, trust) is our access control. A where filter on the query is what stops cross-role leaks.

FastAPI

build

The same web framework as the Part 1 chatbot.

In Part 2: exposes POST /ask and POST /ingest, with the role coming from a token. Every attack tool hits this one endpoint.

LangChain

optional

A framework of ready-made RAG parts: document loaders, text splitters, retrievers and chains.

Our pick: plain Python plus the Chroma client, so every security check is a visible line of code you can point to in the demo. We may borrow LangChain's text splitter.

LlamaIndex

alternative

Another RAG framework focused on indexing and querying documents. It does the same job as LangChain.

Our pick: not used. Listed in the README as an option; one framework is enough, and none is needed for a pipeline this size.

Attack it (reused from Part 1)

Promptfoo

attack

A fast test runner for LLM apps: a YAML file of prompts plus checks on each answer.

In Part 2: a test matrix of employee-role queries that fails if any answer contains the HR canary, plus its RAG-focused red-team plugins for document exfiltration and poisoning.

PyRIT

attack

Microsoft's framework for scripted, multi-step attacks with converters and scorers.

In Part 2: cross-domain (indirect) prompt injection. It plants a payload in a document, asks a normal question, and scores whether the answer obeyed the hidden instruction.

Garak

attack

NVIDIA's vulnerability scanner with hundreds of canned probes.

In Part 2: the latentinjection probe family, which hides injections inside documents, reports and résumés. A good model-level baseline before we test the full app.

Label the findings

OWASP LLM Top 10

standard

The industry list of the ten most common LLM-app vulnerabilities. Gives each finding a name a security team recognises.

In Part 2: LLM01, LLM02 and LLM08.

MITRE ATLAS

standard

A catalogue of real adversary techniques against AI systems, like ATT&CK for machine learning.

In Part 2: each finding gets a technique ID (e.g. indirect prompt injection, RAG poisoning) so it reads like a threat-intel report.
